02 슈퍼센트 · H2팀 · 2026.07 ~ 현재 · 잠실 Company Project

역할을 나눈 AI 세션을 그래프로 연결했습니다

AI 세션을 노드, 작업이 넘어가는 경로를 엣지로 보고 흐름을 설계했습니다. 구현을 맡은 세션은 스스로 완료 처리를 할 수 없습니다.

노드별 역할
  • 사용자요구 사항을 전달하고 결정을 내립니다. PD하고만 대화합니다.
  • PD스펙 작성, 작업 배분, 병합을 맡고 코드는 직접 쓰지 않습니다.
  • 워커각자 격리된 작업 공간에서 구현·커밋하는 독립 AI 세션입니다.
  • QA구현에 참여하지 않은 세션입니다. Unity MCP로 게임을 조작해 수치와 스크린샷으로 판정합니다.
설계 원칙
  • 착수 조건스펙과 사전 검토가 없는 작업은 배분 스크립트가 받지 않습니다.
  • 재작업실패하면 QA가 워커에게 바로 돌려보내고, PD는 이 과정에 끼지 않습니다.
  • 기록세션 사이에는 짧은 메시지만 주고받고, 자세한 내용과 상태는 파일에 남깁니다.
  • 병합Unity 에디터는 한 번에 한 세션만 쓸 수 있어 PD가 하나씩 병합합니다.

03 슈퍼센트 · H2팀 · 팀 AI 개발 체계 — 문제와 해결 Company Project

구현한 AI가 스스로 검증하지 않도록 바꾼 과정

PROBLEM

AI의 자기 검증을 믿을 수 없었습니다

AI 코딩 에이전트에 구현을 맡기니 속도는 빨라졌지만, 같은 세션이 구현과 검증을 함께 하면 자기가 만든 흐름대로만 테스트했습니다. 기준은 모두 통과했다는데 실제로 게임을 켜 보면 깨져 있는 일이 반복됐습니다.

RESULT
  • 기능 스펙 100+ 개를 이 흐름으로 진행
  • 스펙·검증 기록이 git에 남아, 세션과 사람이 바뀌어도 pull만 받으면 맥락이 이어짐
  • 기획자도 같은 규약으로 스펙 작성부터 AI 구현까지 진행 (전체 스펙의 약 20%)
  • 팀 커밋의 절반 이상을 담당
LESSON

AI가 틀릴 수 있다고 전제하고
검증 단계를 따로 두는 것이
프롬프트를 다듬는 것보다 중요했습니다.

SOLUTION

AI 세션마다 역할을 나눠 팀처럼 운영했습니다

1. 스펙 주도 개발

작업을 시작하기 전에 수용 기준을 적은 spec.md부터 만들고, 설계가 바뀌면 문서를 먼저 고치도록 팀 규칙으로 정했습니다. 커밋할 때마다 스펙과 진행 문서가 서로 맞는지 훅이 자동으로 검사합니다.

2. 구현·검증 세션 분리

작업 전에는 QA 세션이 수용 기준을 먼저 검토하고, 작업 후에는 구현에 참여하지 않은 QA 세션만 완료를 판정합니다. QA 세션은 Unity MCP로 게임을 직접 조작해 수치와 스크린샷으로 확인하고, 확인 과정은 다시 쓸 수 있는 테스트 코드로 남깁니다.

3. 병렬 작업

총괄(PD) 세션이 여러 워커 세션에 작업을 나눠 주고 결과를 병합하는 스크립트를 만들었습니다. 사전 검토를 거치지 않은 작업은 배분되지 않습니다.

4. 도구에 상관없는 공유 규칙

규칙 원본을 특정 AI 도구에 묶이지 않는 파일로 두고 Claude Code와 Cursor 설정에 연결했습니다. 팀원 누구나 저장소만 받으면 같은 방식으로 작업할 수 있습니다.

  • 자동으로 되는 것: 세션을 열면 핵심 규칙을 불러오고 커밋 훅이 설정되어, 사람이 직접 커밋할 때도 문서 검사가 실행됩니다.
  • 직접 챙기는 것: 상황별 세부 규칙은 핵심 규칙의 안내를 보고 찾아 읽고, QA 검증은 세션을 따로 띄워 요청합니다.

04 슈퍼센트 · H2팀 · 팀 AI 개발 체계 — 에이전트 스킬 Company Project

반복 업무는 에이전트 스킬로 만들어 팀과 공유합니다

팀 저장소에 10여 개를 올려 함께 쓰고 있고, 그중 6개를 소개합니다.

01

QA 판정

스펙의 수용 기준을 테스트 항목으로 먼저 정리하고, 게임을 실행해 확인한 뒤 통과·실패 리포트를 남깁니다.

수용 기준→테스트 항목→실행 확인→판정 리포트
02

플레이테스트

Unity MCP로 게임을 조작해 수치와 스크린샷으로 확인하고, 확인 과정을 다시 쓸 수 있는 테스트 코드로 저장합니다.

Unity MCP 조작→수치·스크린샷→테스트 코드 저장
03

빌드 자동화

사내 빌드 서버에 빌드를 요청하고, 끝나면 성공 여부를 확인해 변경 내역과 함께 팀 채널에 올립니다.

빌드 요청→완료 대기→성공 여부 확인→결과 공유
04

기획 데이터 배포

기획 데이터 시트를 수정해 새 버전으로 배포하고, Unity에 받아 제대로 반영됐는지 비교합니다.

시트 수정→버전 배포→Unity 반영→결과 비교
05

Figma → Unity UI

Figma로 화면을 그리거나 받은 시안을 Unity UI 프리팹으로 옮기고 검수합니다.

Figma 설계·시안→UI 프리팹 변환→검수
06

에러 알림 분석

에러 알림이 오면 콜스택을 따라 코드를 추적해 원인·결과·대응을 정리한 답글 초안을 쓰고, 확인을 받은 뒤 올립니다.

콜스택 추적→답글 초안→확인 후 게시

  • ODE 추상 클래스와 ODESolver 클래스를 설계하여 범용 4차 Runge-Kutta 솔버 프레임워크 구축
    • ODE(Ordinary Differential Equation, 상미분방정식): 물리 모델의 미분방정식 우변을 정의하는 추상 클래스, ODESolver: ODE를 입력받아 Runge-Kutta로 수치 적분하는 솔버 클래스
  • k1~k4 가중치(1:2:2:1)로 결합하는 고정밀 수치 적분으로, 오일러 방법 대비 정확도를 비교 검증
    • 오일러 방법은 1차 근사로 비선형 시스템에서 오차가 급격히 누적되는 반면, RK4는 4차 정밀도로 속도에 따라 비선형으로 변하는 공기저항·토크 계산에 적합

자동차 동역학 모델링

  • 엔진 RPM 구간별 비선형 토크 곡선 모델링 (0~1000 / 1100~4600 / 4600+ RPM)
  • 6단 기어비 배열과 RPM 보상 기어 변속(ShiftGear) 구현
  • 공기저항·롤링마찰·엔진 토크를 반영한 종방향 가속도 공식을 ODE 우변 함수로 구현
    • ODE 우변 함수: dy/dt = f(t, y) 형태에서 f에 해당하며, 현재 속도·RPM 상태를 입력받아 가속도를 반환하는 함수
